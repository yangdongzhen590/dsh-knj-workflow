F01

工作流图模型与静态校验

graph.jsvalidateWorkflow 纯函数、无 IO、Host 与测试共用

数据结构

一张图 = {id,name,description?,schemaVersion:2,revision,inputs[],nodes[],edges[]}。6 种节点：start | end | task | gateway-xor | gateway-and | human。边可带条件 when:{field,op:'eq'|'neq'|'in',value} 与 default:true 兜底。

task.body = {prompt,mode:'single'|'parallel',parallelItems?,output?:JSONSchema}；human.routes = [{label,to,tone?}]（兼容旧 approveTo/rejectTo，自动推导为「通过/驳回」）。

校验

validateWorkflow（graph.js:124-247）12 类检查，最狠的四条：

  • start/end 各恰一个；节点 id 唯一、type 必须在白名单
  • 孤立节点：除 start 外入度必须 >0 —— 但 human.routes 被当作虚拟边计入度数（topoEdges），否则「驳回→修复」的回环会被误判孤立
  • XOR 必须有多出边 + default + 非 default 边必须带 when；task 多出边同理（否则是永远命不中的死边）
  • human 不得出现在并行分支内：用 branchNodes 分析 split→join 区间，含虚拟边（否则并行分片里的审批会静默吞掉）

保存时 prepareWorkflowForSave（:374）通过校验后原地规范化 inputs、写 schemaVersion:2、revision = existing.revision+1。orderTaskNodesByFlow（:397）从 start BFS（真实边 + 虚拟边）只收 task 节点 → 决定进度条顺序。

刻意不做

不检查可达性（只查入度，不查能否走到 end）、不做环检测（驳回回环合法）、不校验 prompt 非空 / JSON Schema 合法性 / maxRuns 范围 / displayFrom。这些全部留到运行期由编排器抛错。

输入参数名黑名单 /[\s.\\/:*?"<>|]/（graph.js:26），点号必须拒——${inputs.a.b} 按 . 逐段取值会永远取不到，注释写明了这个原因。

坑

运行证据 实跑 repro-zero-outedge.mjs：task 节点零出边时编排器会抛「流程在此断头」，但 validateWorkflow 仍返回 {ok:true}。坏图能存进库，只在跑的时候炸 —— 这是「半修」状态。

画布编辑器：1,393 行的单组件怎么画出可交互的图

client.js class GraphEditor 1004-2396 · 占全文件 32%

渲染

自研 inline SVG，没有 canvas、没有图库、没有 JSX（全文件 784 处 react.createElement）。renderSvg()（1857-1881）画：网格背景（CSS 双层 linear-gradient）+ 节点 + 边 + 连线预览。

节点几何按类型写死：任务/人工矩形 120×44、网关菱形半对角 30、起止胶囊 60×36；端口是节点右侧蓝点，end 无出端口。箭头用 <defs><marker>（5 色）+ 手工三角兜底（注释：绕开 marker 渲染可靠性问题）。

连线路由

7 个几何函数构成一套正交+样条混合路由：incomingPortSlot（同目标多入边分配槽位）→ flowPorts（按相对角度选边，±12px 散布）→ flowObstacles（把其它节点当障碍）→ routeEdgeKnee（直通 / 竖列 3 段避卡 / V-H-V 上下包抄 ±60..150 / 兜底中线）→ smoothCurvePath（Catmull-Rom 转三次贝塞尔）→ routeEdge（先 21 点采样判断直连是否撞卡，再决定直线还是样条）。

这套算法在 Host 的 graph.js:498-638 有一份镜像实现，两边注释都写着「两处需同步修改」。

交互
  • 拖节点：startDrag 记偏移 → move 时 patchNode(..., record=false) 不入历史 → up 时统一 pushNow 入栈（拖拽坐标不逐帧进 undo）
  • 拖线：端口 mousedown + stopPropagation → move 时用 70×42 命中框找目标 → up 时写入边；虚线实时预览
  • 缩放/平移：滚轮平移（scrollLeft/Top）、缩放 0.5–2.0、home() 复位；所有命中判定都先过 canvasPoint()（同时处理 getBoundingClientRect + 滚动 + zoom）
  • 环边判定：isUpstream(a,b) DFS，成环的边画红色虚线警示
撤销栈

快照式历史（JSON 深拷贝），上限 101；pushHistory 与栈顶相同则去重；scheduleCommit 对文本输入做 600ms 防抖合并为一步；flushPending 保证撤销/保存前顺序正确。Ctrl+Z / Ctrl+Y / Ctrl+Shift+Z，焦点在输入框时不拦截。保存成功 / 导入成功 → 重建基线（hours=[]、redo 清空）。

坑

①「输入参数声明」面板走 setWf，不进 undo（注释明说「名称/ID 元数据不进 undo」）→ 改输入参数按 Ctrl+Z 没反应；②assistChanged 高亮在保存成功后不清空，只有新对话或撤销才清 → 绿色高亮残留；③ 硬编码浅色底 6 处，暗色主题下失效。

AI 对话改流程：把黑盒 subagent 包装成「实时过程流 + 整轮撤销」

index.js runAssist/startAssist/_startAssistStream 601-1074 · client.js 对话坞 1405-1472

两段式

发起：POST /assist {workflow, message, history} → 202 {requestId}（异步，不阻塞 HTTP）。过程：客户端每 700ms 拉 GET /assist/progress?id=&since=<lastSeq>，按 seq 游标增量追加，拿到 done 才收。

为什么不是 SSE/WS：宿主插件只注册了 prefix HTTP 路由，长连接在 cordis 生命周期里更难清理；轮询 + 游标是这个规模下最省事的选择。

Host 侧

runAssist → 建 prompt（summarizeWorkflow 图摘要 + ASSIST_RULES 12 节规范 + 最近 8 条历史）→ 读 assist-script.js 源码 → engine.start → 等 run.result → applyEdits(workflow, edits)。

Host 是唯一的写图权威：客户端把 before 整图发过去，收到的是已校验完的最终图 + applied[]（生效）+ rejected[{action,reason}]（被拒+原因）。客户端不做逐条回放。

动作引擎

8 种动作 add_node/set_node/remove_node/add_edge/set_edge/remove_edge/set_routes/set_meta，三层防护：

  • 动作级语义预检（assist-edits.js:74-162）：禁删 start/end；set_node 字段白名单（禁写 x/y/id——布局归客户端，AI 不许碰）；禁自环/重复边；set_routes 仅 human 且 label 唯一
  • 应用：全部 clone 后返回新对象（原图深度不可变）
  • 整批终检：validateWorkflow 不过 → 整批回滚（返回原图、applied=[]）

被拒动作不阻断后续动作（逐条 reject 而非整轮失败）。

最巧一手

AI 脚本用 schema 输出，模型因此不产生普通 text 块，正文藏在 structured_output 工具的参数增量里。Host 从 tool-call 增量 args 里用正则截 "reply":"…" 的未闭合 JSON 字符串前缀，再用容错解码器（尾部不完整转义直接丢弃）还原 → 把结构化输出「伪装」成流式正文（index.js:862-898）。这就是对话坞里那个逐字输出的正文效果。

过程流采集

三级数据源回退：readSession(childId).events → readSurface(childId).events → listEvents(childId)；同时挂 ctx.on('session/event') 做实时。注释给出实测依据：「读持久化日志前 162s 无数据、172s 一次性到 1878 条（按批 flush），所以实时性必须来自事件通道，轮询仅兜底」。轮询 2s 一次 + done 后补采最后一帧。

坑

运行证据 真实 433 次请求里 220 次（51%）降级为「只有阶段级过程」（SESSION_QUERY_SESSION_NOT_FOUND 199 次），而 UI 不告知用户降级。另外 token 用量只在 childId 存在时才渲染——没有 childId 时即使有 usage 也不显示。

新建任务：需求可空、标题自动派生、长需求不炸上下文

index.js POST /tasks 1755-1854 · requirement.js 86 行 · client.js NewTaskModal 2505-2927

标题

表单没有标题输入框。标题由 Host 派生：deriveTaskTitle(description) = 首条非空行 → 去 markdown # → 按码点截 50 个字符（Array.from，不会切坏代理对）；空则 未命名任务 MM-DD HH:mm。标题恒非空，看板/命令平面都依赖这点。

长需求

三个常量：INLINE_MAX = 8000 字符（按码点）、HEAD_MAX = 6000、文件名 requirement.md。≤8000 全文进 prompt；>8000 则「前 6000 字 + […… 省略 N 字。完整需求已落盘：<path> …]」，完整全文落盘到 tasks/<id>/requirement.md。

落盘位置从路由搬到了 startTask（spillRequirementBeforeRun）：因为调度器构造 task 不走路由，原来放在路由里导致「长需求对节点等于丢失」。改成启动前单点 owner 后，HTTP/调度器/命令/resume/rerun 全入口覆盖，且幂等。

请求体

readBody（index.js:1556-1595）按 Buffer 累积、最后一次性 UTF-8 解码。注释记录事故：旧实现 raw += chunk 每块各自解码，多字节中文跨块被截成 U+FFFD ——「粘贴大段中文需求」正是核心场景，超 ~64KB 必乱码。上限 MAX_BODY_BYTES = 1e7（按字节，因为中文 3 字节/字）。

超限时不 req.destroy()，改为抽干剩余请求体 —— 否则路由还没写响应，客户端只看到 socket hang up，设计好的 413 永远到不了调用方。

执行模型

可选 model/provider；下拉数据来自 GET /models，而它不依赖 llm 服务（Host 插件 realm 拿不到），而是手写 YAML 缩进扫描器去读 ~/.dsh/settings.yaml 的 agent-default-model 与 llm-pi-ai.providers[].models[].id——注释：避免内置猜测出无效 provider id 导致 subagent 启动失败。

坑

运行证据 真实 23 个任务里需求最长 28 字、4 个空需求 → 长需求路径从未被真实触发，只有 13 条单测背书。另有 1 个 task.json 带 UTF-8 BOM，朴素 JSON.parse 直接失败（写盘侧没有统一「无 BOM」约束）。

附件与文件入参：从「表单里选的文件」到「节点手里的绝对路径」

uploads.js 157 行 · attachments.js 184 行 · index.js 1462-1519

两段式

暂存（任务还不存在时）：POST /uploads {name,dataBase64} → uploads/<uploadId>/<safeName>，24h TTL。文件名先消毒：取 basename（\ 和 / 都切）→ 去 <>:"|?* 与控制字符 → 去首尾空白/点 → 超 120 字符保留扩展名截断。uploadId 必须匹配 ^up-[a-z0-9]+-[a-z0-9]{8}$ 才允许拼路径。

物化（启动前）：copyFile 到 <cwd>/.knj-inputs/<taskId>/，把绝对路径写进 inputs.<参数名> 或 inputs.附件，然后丢弃暂存。为什么是 copy 不是 rename：暂存常在 C 盘、工作区可能在别的盘，跨盘 rename 在 Windows 上 EXDEV 失败。

两种入参
  • 内置通用附件（无需声明）：固定键 inputs.附件 = 换行拼接的绝对路径串，最多 20 个；节点 prompt 写 ${inputs.附件} 自己解析
  • 声明式文件入参：工作流里声明 {name,label,required,type:'file'}，满足方式二选一——上传（fileInputs）或只给路径（inputs.<name>，相对路径按 task.cwd 解析成绝对路径并 stat 校验存在）

节点只拿到路径，不注入文件内容，也不塞进需求描述——文档解析由节点自己写 prompt 完成。

最巧一手

同名文件冲突时如何区分「我上次跑留下的」和「用户这次新选的同名文件」？.knj-materialized-names.json 记录本任务物化过的名字：是自己的旧文件 → 覆盖（否则每次运行堆出 2-x、3-x）；是用户新选的同名文件 → 加序号（2-名字.ext），绝不覆盖。失败时把本次写入的文件全删，不留半套材料。

失败语义

拒绝启动，不静默少文件：暂存失效 → 报出文件名；必填入参缺失 → 400；路径指向的文件不存在 → 报参数名与解析后的路径。代码注释一句话概括原则：「文件入参指向空比启动失败更糟」。工作区还会自动写 .knj-inputs/.gitignore（内容 *），让用户上传的东西不进他的版本库。

验证

assertInsideDir 即使消毒被绕过也再校验目标真在目录内（relative + 绝对路径 + 盘符三重判断），并特意导出给测试直接打靶——注释说否则「护栏就是没人验证的死代码」。

F07

编排执行：沙箱里那 410 行才是真正的「引擎」

orchestrator.js 410 行 · 无 fs / 无 require / 无网络

沙箱约束

脚本以源码字符串交给 workflow 引擎，在隔离沙箱里跑；可用 API 只有 agent(prompt,opts)、parallel(thunks)、phase(id)、log(msg)、args。所以：图路由/条件/宽松相等/模板解析全部内联复制自 graph.js（注释「勿偏离」）；断点落盘不能自己写文件，只能 log('[knj-checkpoint]'+JSON) 上报让 Host 写。

主循环

executeUntil(nodeId, joinId)（:264-393）：start 出发，按节点类型分派：

  • task：skipSet 命中则跳过（断点恢复）→ countRun 计数（超 maxRuns 抛错，默认 3）→ prehook → 拼 prompt（只自动加两段：[人工意见]、[工作目录]，其余靠显式 ${...}）→ agent() → checkpoint → posthook
  • gateway-xor：按 when「声明顺序最先命中」路由，default 兜底（带条件的 default 也参与匹配）
  • gateway-and split：findJoin BFS 找第一个多入边 gateway-and → parallel(分支)；任一失败=整体失败；分支内 human 暂停必须向上传播
  • human：无决策则 return {paused:true}
  • 并行节点：body.mode==='parallel' → 派 N 个 subagent 跑同一 prompt，结果合并为数组，各写 <node>-i.json
引用解析

resolveRefs 正则 /\$\{(?:ctx\.)?([^}]+)\}/g；resolveRefRaw 按 . 逐段、贪心最长 key 前缀匹配（所以 ${inputs.附件}、${node.field}、${task.id} 都能解析）。解析不到 → 空串，避免把 ${...} 原文漏进 prompt 污染模型输出。

条件比较用 looseEq：true↔'true'、5↔'5' 双向宽松 —— 因为 subagent 输出可能是字符串化的布尔/数字，而 UI 存的是另一种形态。

教义

失败即抛，绝不吞错（:395-397）：脚本正常 return 会被引擎判 stopReason=completed，失败任务会被误标 success。所以节点无输出、并行全失败、安全步数（1000）触发循环都显式 throw。

file/dir 是 UI 展示语义，不是 JSON Schema 类型 —— 传给 subagent 前归一化为 string，否则 schema 校验直接失败。

F08

断点、续跑、单阶段重跑：三个入口，三套清理策略

index.js /rerun-stage 1886 · /resume 1943 · monitorRun 1305

断点怎么来

编排器每完成一个 task 节点就 log('[knj-checkpoint]'+JSON)；Host 的 monitorRun 监听 workflow/log，前缀匹配后 JSON.parse 并 writeStage(taskId, nodeId, output)。注释说得很直白：「subagent 常不遵守写文件指令，不能依赖它」 —— 所以编排器 prompt 里那句「请把结果写到 stages/xxx.json」基本是噪声，真正落盘的是 Host。

resume

读 stages/*.json 组装 initialResults（同时成为 skipSet）。并行节点要识别 -N 后缀并校验分片数完整且序号连续（parallelItems 默认 3）。不清文件；stageStates 保留 done，把 skipped/failed 重置 pending 并清 sessionIds。

rerun-stage

只取目标节点之前的断点（stage 文件优先，回落 results.json），然后删掉目标及之后的 stage 文件（用正则 ^(.*)-(\d+)$ 去掉分片后缀）。这样重跑一个阶段不会把后面已完成的结果误当缓存。

rerun 全量

POST /resume?mode=rerun：initialResults={} + 删整个 stages 目录 + stageStates 全量重置。

坑

maxRuns 是按单次 run 计数，resume 后清零 → 反复点「继续」可以无限重试，死循环保护只在单 run 内成立。真实数据里确实靠这个绕过过一次（fix 跑 4 次触发熔断后任务被 cancel）。

F09

人工审批：为什么需要「决策重放」三件套

index.js /decide 2030-2100 · orchestrator.js 34-44 / 361-382

用户侧

跑到 human 节点 → 任务进 waiting-human，详情里出现审批卡（展示 displayFrom 指定节点的产物，可预览 md/文件）→ 按钮文字是流程里配的（routes[{label,tone}]，可多条），可填意见 → 决策后意见注入下游节点 prompt。

Host 侧

POST /decide {decision, feedback?}：校验 status===waiting-human → 兼容旧值 approve→通过 / reject→驳回 → 把历史决策做成 decided = buildDecidedMap(task)（每个 human 取最后一条）→ 追加 decisions[] → startTask({decision, decided, initialResults: humanState.results})。遇 409 会回滚：恢复 humanState、status=waiting-human、删掉刚追加但没被消费的决策。

三件套

这是全项目最微妙的 20 行。问题：人工节点暂停后，decide 会重新走图；如果图里有两个顺序人工节点，或者驳回→修复→又回到同一个人工节点，历史决策会被反复重放，导致 fix/submit 空转到 maxRuns 超限，人工节点永远不再触发（真实任务 task-mttp8q71 / task-mttz5ok7 现场）。解法：

  • decidedMap：已审批过的 human 直接走最后去向，不再暂停
  • humanReleased：每个 human 在单次 walk 内只自动放行一次 —— 去向若把流程带回同一个 human（驳回回环），第二次到达 = 新一轮审批，必须暂停
  • skipSet.delete(route.to)：去向目标必须重新执行（接受人工意见），不能被断点跳过
验证

运行证据 repro-ts-review-loop.mjs 实跑 exit 0：驳回后 fix/submit 各跑 1 次并重新暂停在同一 human —— 这三件套确实生效了。另有 repro-decide-order.test.js 守住「409 时不得改状态」。

进度百分比 progressPct：success 直接 100；否则 done / 非 skipped 阶段数。三套状态元数据并存：任务级 STATUS_META（6 态）、阶段级 STAGE_META（5 态）、运行图 RUN_STATUS（7 态含 waiting/passed）。

看板 5 列 = 待执行 / 运行中 / 待人工处理 / 成功 / 失败·已取消；详情里有横向步骤条（注：横向步骤条组件其实在已死的 TaskDetail 里，当前详情用的是节点卡片 + 运行效果图）。

事件驱动

Host 侧 monitorRun 把 workflow/phase（当前阶段）、workflow/agent-start（追加 sessionIds）、workflow/agent-end（标 done）翻译成 stageStates 增量并落库，前端下次轮询就能看到。一个坑：多轮复用同一节点时，上一轮的 done 会挡住新状态 —— 所以 agent-start 会强制置回 running（清 finishedAt/error、刷新 startedAt），monitor-stage-status.test.js 守的就是这条。

未文档化的亮点

坑

状态机跨三层（Host 真源 finalizeTask+monitorRun、图推导 graph.deriveRunGraphStates、UI 的 3 处状态表 + 1 份镜像推导）。只改一层必然出现「后台 success、界面 running」。

命令平面与定时调度：两个「可选接口」

index.js registerCommands 2228-2302 · createKnjWorkflowSchedulerService 407-536

斜杠命令

设计意图很好：/dev-task new <标题> / list / status <id> / wf 走命令平面，「结果不进模型上下文」。实现用 ctx.effect(() => commands.register({name,description,execute})) —— 用 ctx.effect 持 disposer 是为了插件卸载/HMR 时注销，否则旧 handler 常驻命令表（引用已卸载的 store，执行即幽灵副作用）。

调度服务

ctx.provide('knjWorkflowScheduler', {listWorkflows, createAndStartScheduledTask})；dsh-scheduler 侧按字符串服务名取用（executionKind === 'knj-workflow'），并额外要求插件提供 stageAttachments（缺失时调度器提示「请更新该插件后重启」）。没有共享类型/版本校验，所以升级必须两边一起。

调度路径的两个特殊设计：不预存 workflowSnapshot（触发时用最新定义）→ 所以 startTask 里刻意回写快照，否则详情页「无流程图」、到人工节点时 humanRoutes(undefined) 抛错整页空白；attachmentsAreReusable 让附件物化后不丢暂存，因为定时任务每次触发都要重新物化。

坑（严重）

运行证据 /dev-task 命令在 DSH 0.2.1 上注册失败 已修复 2026-10-24：宿主 CommandDefinition 要求 handler 必填，插件传的是 execute，宿主直接抛 TypeError: command "dev-task" handler must be a function。cordis 的 effect() 会同步重抛 → 该错误从 store.init().then 冒到 .catch，日志出现 init failed；但 HTTP API 仍正常（registerRoutes 在它之前执行）。这就是「代码里写着、菜单里没有」的功能。

F12

并发、取消与卸载：不死锁、不漏 run、不烧钱

index.js runs Map 590 · cancelTask 1379 · apply 2319-2322

并发守卫

三层：路由预检 isRunning() → startTask 内同步占位（在任何 await 之前 runs.set）→ 抛 RunAlreadyActiveError 由路由转 409。这堵住了「取消后立即续跑」把任务误标 failed 的窗口，也堵住双份 subagent 的 LLM 成本。

生命周期

run.result 落定后：校验 runs.get(taskId) === run（旧 run 晚到不得覆盖）→ finalizeTask → 四个监听器各自独立 try/catch 地 off（一个抛错不能让 runs 残留）→ runs.delete → run.dispose() → parentHandle.dispose()。

卸载时 ctx.effect(() => () => { disposed = true; bridge?.cancelAll(); })：取消全部活跃 run（否则插件卸载后 subagent 群继续烧 LLM 成本），并用 disposed 标记让晚到的 init() 不再注册路由/命令（注册在已卸载 ctx 上会泄漏成僵尸 handler）。

取消

/cancel 先把 status=cancelled + finishedAt 落库，再调 run.cancel()；DELETE /tasks/:id 先 cancel 再删目录，且 finalizeTask 用 getTask 为空提前返回，避免重建孤儿结果。

坑

finalizeTask 的 paused 分支保留旧 error 不清；cancel 分支把 running 阶段标成 done（有意为之，但 cancelled 任务在详情里看起来「都完成了」）。
