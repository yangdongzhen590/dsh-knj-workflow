2.2插件契约：一个包如何长进 DSH

DSH 的插件是 cordis 行。这个包的「契约面」只有四处：

契约内容作用
cordis.patch.yml- insert: [{id: knj-workflow, name: dsh-knj-workflow, config: {httpPrefix: /devtask}}]bundle 层把插件行追加到 profile cordis 树顶层（宿主 dsh-app-boot 支持 insert 追加语义）
inject = ['webServer','agents']只注入这两个硬依赖；故意不注入 workflowEngine0.2.x 起顶层 enable 只会 pending（等一个永远到不了的 service）；改运行时惰性取
exports["./client"] + dsh.client{platform:"web"}指向 lib/client.js，inject: []dsh-client-modules 扫描时缺这条 export 会直接 throw；空 inject = 不声明信息性依赖边
exports["./orchestrator"]指向 lib/orchestrator.js便利导出；运行时实际用 readFileSync(new URL('./orchestrator.js', import.meta.url)) 读成字符串交给引擎
为什么补丁「只 insert 一行、不改宿主行」——这是版本考古现场 
# cordis.patch.yml 注释原文（节选）
# DSH 0.2.x 起不再需要（也不能）在宿主 realm 里点亮 workflow 引擎行：
#   * workflow-worker-thread 这个行 id 在 0.2 已不存在（补丁会报 entry not found）；
#   * workflowEngine 自 0.1.x rc.8 起就活在 agent-preset 的隔离 realm 里，
#     顶层强行 enable tool-workflow 只会让它 pending（waiting for service: workflowEngine）。
# 插件本身通过 WorkflowBridge.startTask 从「发起任务的 agent scope」惰性取引擎，
# 所以这里只做插入，不再改任何宿主行。

这四行注释比 README 更可信：它记录的是三个版本里踩过的具体报错。

graph.js 名义上是「Host 与编排器共用的纯函数库」，但它后 140 行是 SVG 连线路由几何（routeEdgeKnee/roundedOrthoPath/smoothCurvePath/routeEdge），生产链路根本不用，只被测试和客户端当参考实现。而 client.js 里又独立写了一份同样的算法（client.js:329/385，注释明写「镜像 graph.js…两处需同步」）。加上 nextNode/resolveInputs 是纯死代码，638 行里约 430 行不参与 Host 生产。

2.4Client：零 slot、四个挂载根、一处寄生式接管

这是本次逆向里与 README 差距最大的一块。README 说「左侧栏底部入口 + 右侧栏 better-sidebar 两个 tab」，实际两处都不成立：better-sidebar 在本机未安装且被市场置为 disabled；client.js 的 inject = []，没有任何 slot/扩展点注册。

客户端加载协议也值得记一笔：client.js 第一行是 window.__ModuleLoader__.load({id:"dsh-knj-workflow", factory:(require)=>{…}})，只 require("react") / require("react-dom/client")。没有 SSE、没有 WebSocket：所有数据走同源 fetch('/devtask/…')，实时性靠轮询（看板 3s、AI 过程流 700ms、搜索防抖 300ms、撤销合并 600ms）。

2.5数据模型与磁盘布局

没有数据库。状态就是 JSON 文件，藏在用户家目录；「工作区里只有输入文件，没有任务数据」是刻意的隔离。

~/.dsh/dev-orchestrator/            # dataRoot（可配，DEBUG_LOG 却硬编码这里）
├─ workflows.json                   # {workflows:[{id,name,schemaVersion:2,revision,inputs[],nodes[],edges[]}]}
├─ tasks/<taskId>/
│   ├─ task.json                    # 元数据 + workflowSnapshot 全量副本 + stageStates[] + decisions[] + humanState
│   ├─ requirement.md               # 仅需求 >8000 字时落盘（真实数据 0 例）
│   ├─ results.json                 # 终态/paused 时节点输出汇总
│   └─ stages/<nodeId>.json         # 每节点断点（并行节点为 <nodeId>-1..N.json）
├─ uploads/<uploadId>/<file>        # 上传暂存，24h TTL（表单打开时任务还不存在）
└─ knj-host-debug.log               # JSONL 诊断日志，无轮转，实测 3MB / 2.5 万行

<cwd>/.knj-inputs/
├─ .gitignore                       # 内容 `*`：上传文件默认不进用户版本库
└─ <taskId>/
    ├─ <file>                      # 附件/文件入参的最终位置
    └─ .knj-materialized-names.json # 本任务物化过哪些名字 → 区分「自己上次的」vs「用户新选的同名文件」

关键字段语义：stageStates[] = {id,title,status,startedAt,finishedAt?,sessionIds[]}，status ∈ pending|running|done|failed|skipped；任务级 status ∈ pending|running|waiting-human|success|failed|cancelled，archivedAt 是正交标记（归档不改 status）。

写盘可靠性：三个原语撑起「并发安全」
  • writeJson（index.js:70-94）：先写 tmp-<ts>-<uuid> 再 rename；Windows 上 rename 偶发 EPERM 时回退「删临时文件 + 直接写」最多 3 次（25/50/75ms 退避）。
  • _wfMutate（120-125）：workflows.json 的读-改-写挂在一条串行 Promise 链上，避免并发保存互相覆盖。
  • mutateTask（241-258）：队列内「读最新 → 改 → 写」，所以 monitorRun 的多路事件回调不会后写覆盖先写。
  • assertSafeId（178-182）：^[a-zA-Z0-9._-]+$ 且禁 ..、禁纯点 —— 注释写着「本插件栽过一次 task id 路径穿越」，所有文件路径函数先过它。

2.6执行链路：一次「创建并启动」到底发生了什么

这是整个插件的心脏。POST /tasks 落库后调 WorkflowBridge.startTask，后者是一条 10 步流水线 源码 index.js:1075-1235：

步动作为什么这一步必须在这里
1同步占位并发守卫：runs.has() → 抛 RunAlreadyActiveError；runs.set() 在任何 await 之前完成堵 TOCTOU：否则两个并发请求双双通过守卫，启动两份 subagent（双倍 LLM 成本 + 互踩 stage）
2取 workflowSnapshot（无则读库并回写）运行只用创建时快照，与之后改图解耦；回写是因为详情页/运行图/审批卡都靠它渲染
3-5取 agents/agentPresets → agents.create 建专用 parent 会话（sessionId: knj-task-<id>-<8hex>，meta.cwd + meta.agentPreset，setup: presets.mount）不隔离就会把 workflow 的 subagent 挂到「随机当前会话」下；不挂 preset 则 subagent 连 write/bash/skill catalog 都没有
6四个「启动前」单点：物化文件入参 → 物化附件 → 校验路径型入参 → 落盘长需求放在这里才能覆盖 HTTP / 调度器 / 命令 / resume / rerun 全部入口（曾经写在路由里，调度器路径就漏了）
7task.parentSessionId = parent.id → saveTask前端「执行记录」用它刷新父会话投影；节点跳转也依赖它
8resolveWorkflowEngine → engine.start({script, meta, args, parent})；失败则 parentHandle.dispose()引擎取不到要释放已建的 parent，否则变成泄漏的常驻 agent
9登记 runs/parentHandles → monitorRun(task, run)事件监听必须在 run 启动后立即挂，否则漏掉早期 phase 事件
10任一步抛错：runs 仍是占位标记则删除允许用户修好环境后重试，而不是永久 409
 
// index.js:1196 —— 交给引擎的完整契约
run = engine.start({
  script: this.orchestratorScript || readFileSync('./orchestrator.js', 'utf8'),  // 脚本源码字符串，不是路径
  meta:   { name: workflow.id, description: `${task.title} @ ${workflow.name}` },
  args:   {
    config: workflow,                                  // {id,name,inputs,nodes[],edges[]}
    task:   { id, title, taskDir, inputDescription, description?, storyCode?, cwd? },
    inputs, decision?, initialResults?, decided?, resumeFrom?, rerunStage?
  },
  parent: parent                                        // 专用会话，subagent 都挂在它下面
});

inputDescription 是 Host 侧算好再注入的：≤8000 字给全文，超阈值给「前 6000 字 + 省略说明 + requirement.md 路径」。注释明确禁止在沙箱脚本里重算这份阈值（会与 requirement.js 漂移）。

2.7任务状态机：终态的唯一来源是 run.result

一个「为什么不是 workflow/end」的实现细节 源码

index.js:1320-1323 的注释很直接：workflow/end 事件的 payload 不含 value，拿它 finalize 会用空 results 覆盖真实结果。所以终态只认 run.result，且必须校验 runs.get(taskId) === run——防止旧 run 晚到覆盖新 run。清理时四个监听器各自独立 try/catch，否则一个 off 抛错会让 runs 永久残留（那就是「任务卡 running」的经典现场）。
