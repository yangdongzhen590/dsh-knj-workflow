工作流图模型与静态校验

数据结构

一张图 = {id,name,description?,schemaVersion:2,revision,inputs[],nodes[],edges[]}。6 种节点：start | end | task | gateway-xor | gateway-and | human。边可带条件 when:{field,op:'eq'|'neq'|'in',value} 与 default:true 兜底。

task.body = {prompt,mode:'single'|'parallel',parallelItems?,output?:JSONSchema}；human.routes = [{label,to,tone?}]（兼容旧 approveTo/rejectTo，自动推导为「通过/驳回」）。

校验

validateWorkflow（graph.js:124-247）12 类检查，最狠的四条：

  • start/end 各恰一个；节点 id 唯一、type 必须在白名单
  • 孤立节点：除 start 外入度必须 >0 —— 但 human.routes 被当作虚拟边计入度数（topoEdges），否则「驳回→修复」的回环会被误判孤立
  • XOR 必须有多出边 + default + 非 default 边必须带 when；task 多出边同理（否则是永远命不中的死边）
  • human 不得出现在并行分支内：用 branchNodes 分析 split→join 区间，含虚拟边（否则并行分片里的审批会静默吞掉）

保存时 prepareWorkflowForSave（:374）通过校验后原地规范化 inputs、写 schemaVersion:2、revision = existing.revision+1。orderTaskNodesByFlow（:397）从 start BFS（真实边 + 虚拟边）只收 task 节点 → 决定进度条顺序。

刻意不做

不检查可达性（只查入度，不查能否走到 end）、不做环检测（驳回回环合法）、不校验 prompt 非空 / JSON Schema 合法性 / maxRuns 范围 / displayFrom。这些全部留到运行期由编排器抛错。

输入参数名黑名单 /[\s.\\/:*?"<>|]/（graph.js:26），点号必须拒——${inputs.a.b} 按 . 逐段取值会永远取不到，注释写明了这个原因。

坑

运行证据 实跑 repro-zero-outedge.mjs：task 节点零出边时编排器会抛「流程在此断头」，但 validateWorkflow 仍返回 {ok:true}。坏图能存进库，只在跑的时候炸 —— 这是「半修」状态。

  • 拖节点：startDrag 记偏移 → move 时 patchNode(..., record=false) 不入历史 → up 时统一 pushNow 入栈（拖拽坐标不逐帧进 undo）

物化（启动前）：copyFile 到 <cwd>/.knj-inputs/<taskId>/，把绝对路径写进 inputs.<参数名> 或 inputs.附件，然后丢弃暂存。为什么是 copy 不是 rename：暂存常在 C 盘、工作区可能在别的盘，跨盘 rename 在 Windows 上 EXDEV 失败。

两种入参
  • 内置通用附件（无需声明）：固定键 inputs.附件 = 换行拼接的绝对路径串，最多 20 个；节点 prompt 写 ${inputs.附件} 自己解析
  • 声明式文件入参：工作流里声明 {name,label,required,type:'file'}，满足方式二选一——上传（fileInputs）或只给路径（inputs.<name>，相对路径按 task.cwd 解析成绝对路径并 stat 校验存在）

节点只拿到路径，不注入文件内容，也不塞进需求描述——文档解析由节点自己写 prompt 完成。

最巧一手

同名文件冲突时如何区分「我上次跑留下的」和「用户这次新选的同名文件」？.knj-materialized-names.json 记录本任务物化过的名字：是自己的旧文件 → 覆盖（否则每次运行堆出 2-x、3-x）；是用户新选的同名文件 → 加序号（2-名字.ext），绝不覆盖。失败时把本次写入的文件全删，不留半套材料。

失败语义

拒绝启动，不静默少文件：暂存失效 → 报出文件名；必填入参缺失 → 400；路径指向的文件不存在 → 报参数名与解析后的路径。代码注释一句话概括原则：「文件入参指向空比启动失败更糟」。工作区还会自动写 .knj-inputs/.gitignore（内容 *），让用户上传的东西不进他的版本库。

验证

assertInsideDir 即使消毒被绕过也再校验目标真在目录内（relative + 绝对路径 + 盘符三重判断），并特意导出给测试直接打靶——注释说否则「护栏就是没人验证的死代码」。

编排执行：沙箱里那 410 行才是真正的「引擎」

orchestrator.js 410 行 · 无 fs / 无 require / 无网络

沙箱约束

脚本以源码字符串交给 workflow 引擎，在隔离沙箱里跑；可用 API 只有 agent(prompt,opts)、parallel(thunks)、phase(id)、log(msg)、args。所以：图路由/条件/宽松相等/模板解析全部内联复制自 graph.js（注释「勿偏离」）；断点落盘不能自己写文件，只能 log('[knj-checkpoint]'+JSON) 上报让 Host 写。

主循环

executeUntil(nodeId, joinId)（:264-393）：start 出发，按节点类型分派：

  • task：skipSet 命中则跳过（断点恢复）→ countRun 计数（超 maxRuns 抛错，默认 3）→ prehook → 拼 prompt（只自动加两段：[人工意见]、[工作目录]，其余靠显式 ${...}）→ agent() → checkpoint → posthook
  • gateway-xor：按 when「声明顺序最先命中」路由，default 兜底（带条件的 default 也参与匹配）
  • gateway-and split：findJoin BFS 找第一个多入边 gateway-and → parallel(分支)；任一失败=整体失败；分支内 human 暂停必须向上传播
  • human：无决策则 return {paused:true}
  • 并行节点：body.mode==='parallel' → 派 N 个 subagent 跑同一 prompt，结果合并为数组，各写 <node>-i.json
引用解析

resolveRefs 正则 /\$\{(?:ctx\.)?([^}]+)\}/g；resolveRefRaw 按 . 逐段、贪心最长 key 前缀匹配（所以 ${inputs.附件}、${node.field}、${task.id} 都能解析）。解析不到 → 空串，避免把 ${...} 原文漏进 prompt 污染模型输出。

条件比较用 looseEq：true↔'true'、5↔'5' 双向宽松 —— 因为 subagent 输出可能是字符串化的布尔/数字，而 UI 存的是另一种形态。

教义

失败即抛，绝不吞错（:395-397）：脚本正常 return 会被引擎判 stopReason=completed，失败任务会被误标 success。所以节点无输出、并行全失败、安全步数（1000）触发循环都显式 throw。

file/dir 是 UI 展示语义，不是 JSON Schema 类型 —— 传给 subagent 前归一化为 string，否则 schema 校验直接失败。

断点、续跑、单阶段重跑：三个入口，三套清理策略

断点怎么来

编排器每完成一个 task 节点就 log('[knj-checkpoint]'+JSON)；Host 的 monitorRun 监听 workflow/log，前缀匹配后 JSON.parse 并 writeStage(taskId, nodeId, output)。注释说得很直白：「subagent 常不遵守写文件指令，不能依赖它」 —— 所以编排器 prompt 里那句「请把结果写到 stages/xxx.json」基本是噪声，真正落盘的是 Host。

resume

读 stages/*.json 组装 initialResults（同时成为 skipSet）。并行节点要识别 -N 后缀并校验分片数完整且序号连续（parallelItems 默认 3）。不清文件；stageStates 保留 done，把 skipped/failed 重置 pending 并清 sessionIds。

rerun-stage

只取目标节点之前的断点（stage 文件优先，回落 results.json），然后删掉目标及之后的 stage 文件（用正则 ^(.*)-(\d+)$ 去掉分片后缀）。这样重跑一个阶段不会把后面已完成的结果误当缓存。

rerun 全量

POST /resume?mode=rerun：initialResults={} + 删整个 stages 目录 + stageStates 全量重置。

坑

maxRuns 是按单次 run 计数，resume 后清零 → 反复点「继续」可以无限重试，死循环保护只在单 run 内成立。真实数据里确实靠这个绕过过一次（fix 跑 4 次触发熔断后任务被 cancel）。

人工审批：为什么需要「决策重放」三件套

用户侧

跑到 human 节点 → 任务进 waiting-human，详情里出现审批卡（展示 displayFrom 指定节点的产物，可预览 md/文件）→ 按钮文字是流程里配的（routes[{label,tone}]，可多条），可填意见 → 决策后意见注入下游节点 prompt。

Host 侧

POST /decide {decision, feedback?}：校验 status===waiting-human → 兼容旧值 approve→通过 / reject→驳回 → 把历史决策做成 decided = buildDecidedMap(task)（每个 human 取最后一条）→ 追加 decisions[] → startTask({decision, decided, initialResults: humanState.results})。遇 409 会回滚：恢复 humanState、status=waiting-human、删掉刚追加但没被消费的决策。

三件套

这是全项目最微妙的 20 行。问题：人工节点暂停后，decide 会重新走图；如果图里有两个顺序人工节点，或者驳回→修复→又回到同一个人工节点，历史决策会被反复重放，导致 fix/submit 空转到 maxRuns 超限，人工节点永远不再触发（真实任务 task-mttp8q71 / task-mttz5ok7 现场）。解法：

  • decidedMap：已审批过的 human 直接走最后去向，不再暂停
  • humanReleased：每个 human 在单次 walk 内只自动放行一次 —— 去向若把流程带回同一个 human（驳回回环），第二次到达 = 新一轮审批，必须暂停
  • skipSet.delete(route.to)：去向目标必须重新执行（接受人工意见），不能被断点跳过
验证

运行证据 repro-ts-review-loop.mjs 实跑 exit 0：驳回后 fix/submit 各跑 1 次并重新暂停在同一 human —— 这三件套确实生效了。另有 repro-decide-order.test.js 守住「409 时不得改状态」。

并发、取消与卸载：不死锁、不漏 run、不烧钱

并发守卫

三层：路由预检 isRunning() → startTask 内同步占位（在任何 await 之前 runs.set）→ 抛 RunAlreadyActiveError 由路由转 409。这堵住了「取消后立即续跑」把任务误标 failed 的窗口，也堵住双份 subagent 的 LLM 成本。

生命周期

run.result 落定后：校验 runs.get(taskId) === run（旧 run 晚到不得覆盖）→ finalizeTask → 四个监听器各自独立 try/catch 地 off（一个抛错不能让 runs 残留）→ runs.delete → run.dispose() → parentHandle.dispose()。

卸载时 ctx.effect(() => () => { disposed = true; bridge?.cancelAll(); })：取消全部活跃 run（否则插件卸载后 subagent 群继续烧 LLM 成本），并用 disposed 标记让晚到的 init() 不再注册路由/命令（注册在已卸载 ctx 上会泄漏成僵尸 handler）。

取消

/cancel 先把 status=cancelled + finishedAt 落库，再调 run.cancel()；DELETE /tasks/:id 先 cancel 再删目录，且 finalizeTask 用 getTask 为空提前返回，避免重建孤儿结果。

坑

finalizeTask 的 paused 分支保留旧 error 不清；cancel 分支把 running 阶段标成 done（有意为之，但 cancelled 任务在详情里看起来「都完成了」）。
